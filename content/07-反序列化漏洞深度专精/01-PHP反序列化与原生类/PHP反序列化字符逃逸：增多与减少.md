# 🧮 PHP 反序列化字符逃逸底层机制与数学公式精准推导

> **产生诱因**：绝大多数安全漏洞源于“未过滤”，而字符逃逸漏洞恰恰源于**“多余且错误的过滤”**！
> 业务代码在执行 `serialize()` 生成序列化字符串之后，由于某种安全检测或脱敏需求，调用了 `str_replace()` 或 `preg_replace()` 对字符串进行了关键字替换，紧接着又调用了 `unserialize()`。
> **致命缺陷**：替换函数强行改变了字符串的物理长度，但**没有同步更新前面的长度声明字段（`s:长度:`）**，造成了底层词法解析器的错位与越界！

---

## 0. 基础前置认知与小白扫盲：字符逃逸的底层“挤牙膏”哲学

> [!NOTE] 模块前置语言与工具清单
> - **前置通关必备**：零基础读者强烈建议先通读全局导航 **[[01-零基础入门前置指南与黑话工具字典]]**，掌握安全法律红线、终端命令行、HTTP 报文骨架与黑话字典！
> - **环境依赖**：具备基础 Web 浏览器（Chrome/Firefox）抓包认知或轻量 Python 脚本执行能力。


### 1. 为什么会产生“字符逃逸”？
* **序列化格式的严格契约**：
  * 在 PHP 序列化字符串中，每个字符串变量前面都有一个严谨的“长度计数器”：例如 `s:4:"test";`。
  * PHP 反序列化引擎在读取数据时极其机械死板：**它看到 `s:4:`，就一定会强行向后吞噬整整 4 个字节，并且认为紧跟在后面的 `";` 就是这个变量的终点！**
* **后处理替换破坏契约（祸根之源）**：
  * 很多程序员为了安全，在把对象序列化之后，又用 `str_replace()` 进行了一道敏感词过滤：
    * 比如把违禁词 `hack`（4 个字符）替换成了 `hacker`（6 个字符）——**字符变多**；
    * 或者把违禁词 `fuck`（4 个字符）替换成了空字符串 `""`（0 个字符）——**字符变少**。
  * **灾难诞生**：字符串的实际字符数量改变了，但前面的长度计数器 `s:4:` 却依然留在原地！实际内容与计数器脱节，多出来或者少掉的字符就会像挤压的弹簧一样，把黑客精心伪造的属性代码“顶”到语法结构体中，让其变成一个全新的合法属性！

---

### 2. 字符逃逸两大流派通俗比喻
* **字符变多（向外挤压顶出后门）**：
  * 就像在排队的人群中，内部有人突然膨胀把队伍撑爆，多出来的部分直接被挤到了警戒线外面。黑客把恶意构造的属性（如 `";s:5:"is_admin";b:1;}`）藏在后面，前面膨胀多出来的字符正好把长度计数器填满，后面伪造的属性顺理成章地被当成系统的下一个独立变量！
* **字符变少（向内塌陷吞噬前门）**：
  * 替换后内容凭空消失，但长度计数器依然坚持要吃够那么多字符，于是它只能**强行向后吞噬原本属于正常代码的引号和分号**，形成结构真空，黑客就能把后方的伪造属性顺利拼接上位！

## 一、经典漏洞模式与数据流动模型

```text
[用户输入] ──> serialize() ──> [生成标准串 s:长度:"原文本"]
                                       │
                                       ▼ 【错误过滤：长度发生变化！】
                                preg_replace / str_replace
                                       │
                                       ▼ [长度标记未变，内容物理长度变了]
                               unserialize() ──> 触发字符逃逸！
```

PHP 反序列化引擎是严格按字节数“数人头”读取的：
遇到 `s:5:"abcde";`，解析器从第一个双引号后面开始，**向后机械地硬读整整 5 个字节**。读完之后，紧接着必须遇到闭合双引号 `"` 和分号 `;`。如果遇到的不是预期符号，反序列化立即报错崩溃！

---

## 二、类型一：字符变多型逃逸（向外撑开吐出 Payload）

### 1. 产生场景与核心逻辑
过滤函数把“短字符串”替换成了“长字符串”：
例如将 `x` 替换为 `yy`（每出现 1 个 `x`，物理长度净增 1 字节，$\Delta = 2 - 1 = 1$）。

* **攻击目标**：我们在输入末尾埋伏好一段伪造的恶意属性代码 `Payload`。通过在前面输入足够多的 `x`，在替换发生后，增加的字符把原来的双引号向后猛力“撑开”，**恰好把原有的双引号顶死在 Payload 的最前端**，使得我们埋伏的 Payload 逃逸出字符串边界，被识别为合法的独立属性！

---

### 2. 🧮 变多型逃逸数学推导公式

* 设待逃逸注入的代码片段为 $P$（例如：`";s:8:"password";s:6:"123456";}`）；
* 测量 $P$ 的精确字节长度为 $L_{P}$；
* 设过滤关键字每替换一次带来的长度净增量为 $\Delta = \text{Len}(New) - \text{Len}(Old)$；
* 则需要填入的关键字重复次数 $N$ 满足方程式：

$$N \times \Delta = L_{P} \implies N = \frac{L_{P}}{\Delta}$$

---

### 3. 实战演算推导示例

#### 漏洞代码背景：
```php
class User {
    public $username;
    public $password = 'guest';
}
function filter($str) {
    // 把 1 字节的 'x' 替换为 2 字节的 'yy'，净增量 Delta = 1
    return str_replace('x', 'yy', $str);
}

$user = new User();
$user->username = $_GET['user'];
$res = filter(serialize($user));
$obj = unserialize($res);
if ($obj->password === 'admin_pass') {
    echo "Flag{Success_Escape!}";
}
```

#### 推导步骤：
1. **构造希望逃逸的恶意属性片段**：
   我们需要闭合前引号，并强行将 `password` 篡改为 `admin_pass`，并闭合最外层大括号抛弃原有的尾部垃圾：
   ```text
   ";s:8:"password";s:10:"admin_pass";}
   ```
2. **精确数出该片段的字节长度**：
   `";s:8:"password";s:10:"admin_pass";}` 共有 **36 个字符/字节**（$L_P = 36$）。
3. **计算需要填充的关键字数量**：
   因为每次 `x` 变 `yy` 净增 1 字节（$\Delta = 1$），所以需要填充：
   $$N = \frac{36}{1} = 36 \text{ 个 } 'x'$$
4. **组装最终提交的 `username`**：
   `36 个 x` + `";s:8:"password";s:10:"admin_pass";}`

#### 🔍 底层错位全景透视：
* **序列化完成时**：`username` 声明长度为 $36 + 36 = 72$：
  `...s:72:"xxxxxxxx...(36个)...";s:8:"password";s:10:"admin_pass";}";s:8:"password";s:5:"guest";}`
* **过滤函数替换后**：36 个 `x` 膨胀为 72 个 `y`！
  `...s:72:"yyyyyyyyyyyyyyyyyyyy...(整整72个y)...";s:8:"password";s:10:"admin_pass";}";s:8:"password"...`
* **反序列化解析器入场**：
  引擎看到 `s:72:`，向后数完 72 个 `y`，正好遇到双引号 `"`！
  引擎判定字符串读取圆满结束，接着向下解析：遇到了 `;s:8:"password";s:10:"admin_pass";}`，成功以管理员密码反序列化出对象！原有的 tail 垃圾由于已被大括号提前闭合，被完全丢弃！

## 三、类型二：字符变少型逃逸（向内吞噬吃掉属性）

### 1. 产生场景与核心逻辑
过滤函数把“长字符串”替换成了“空”或更短的字符串：
例如将 `flag` 替换为 `""`（每出现 1 个 `flag`，物理长度净减 4 字节，$\Delta = 4$）。

* **攻击难点**：变少不会向外吐出代码，反而会向后“贪婪吞噬”！
* **攻击逻辑**：
  我们需要控制**两个属性**（例如 `$username` 和 `$nickname`）。
  利用在 `$username` 中填入大量的 `flag`，过滤后 `flag` 蒸发消失，但 `s:长度:` 仍然保留原长。
  引擎为了补足缺额的字节数，**被迫向后疯狂吞噬，一口把 `$username` 的后引号、分号、以及 `$nickname` 的键名全部当作字符串吃进肚子里！**
  随后，我们在 `$nickname` 的值里面，填入我们真正要逃逸的代码，完成偷天换日！

---

### 2. 🧮 变少型逃逸数学推导公式

* 观察被吞噬的中间固定垃圾模板结构（从 `$username` 的后引号到 `$nickname` 的前引号内部）：
  垃圾结构形如：`";s:8:"nickname";s:长度:"`
* 测量这段必须被吃掉的固定字符长度为 $L_{trash}$；
* 若我们要在 `$nickname` 前部补充 $K$ 个对齐字符让其凑整；
* 每次替换减量为 $\Delta$；
* 求解满足整除关系的方程式：

$$(L_{trash} + K) \pmod \Delta == 0 \implies N = \frac{L_{trash} + K}{\Delta}$$

---

### 3. 实战演算推导示例

#### 漏洞代码背景：
```php
class Profile {
    public $name;
    public $sign;
    public $role = 'guest';
}
function filter($str) {
    // 4 字节的 'flag' 被剔除置空，减量 Delta = 4
    return str_replace('flag', '', $str);
}
```

#### 推导步骤：
1. **分析序列化生成的中间垃圾**：
   正常情况下序列化串中连接 `$name` 和 `$sign` 的中间部分为：
   `";s:4:"sign";s:【sign的实际长度】:"`
   数一下这段垃圾在固定情况下的长度。
   假设我们在 `$sign` 中输入精心构造的：
   `A";s:4:"role";s:5:"admin";}`（其中 `A` 是用来对齐字节的填充符）
   那么需要被前一个字段完全“吞掉”的目标垃圾就是从 `$name` 结束引号直到 `A` 之前的内容：
   `";s:4:"sign";s:30:"`
2. **精确数出中间被吞垃圾的长度**：
   字符串 `";s:4:"sign";s:30:"` 正好有 **20 个字符**（$L_{trash} = 20$）。
3. **计算需要的过滤词数量**：
   因为 $20$ 可以被 $\Delta = 4$ 整除：
   $$N = \frac{20}{4} = 5 \text{ 个 } 'flag'$$
4. **组装双参数攻击载荷**：
   * `name = flagflagflagflagflag` (5个flag，共20字节)
   * `sign = A";s:4:"role";s:5:"admin";}`

#### 🔍 底层吞噬全景透视：
* **过滤后**：5 个 `flag` 瞬间蒸发归零，但前面依然标记为 `s:20:`！
* **引擎被迫吞噬**：引擎向后硬数 20 个字符，正好把 `";s:4:"sign";s:30:"A` 前面的部分全部吃掉，当成了 `$name` 的值！
* **破茧而出**：紧接着引擎读到了 `";s:4:"role";s:5:"admin";}`，把 `role` 成功反序列化为 `admin`，实现提权！
